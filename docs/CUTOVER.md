# เปลี่ยนไปใช้ระบบสต็อก

## เตรียมข้อมูล
1. หยุดทำรายการชั่วคราว ให้ทุกเครื่องซิงค์คิวเดิมจนหมด ตรวจรายการค้างเทียบประวัติจริงก่อนส่งซ้ำ
2. ยืนยันว่าข้อมูลล่าสุดอยู่ใน Supabase ถ้ามีข้อมูลเฉพาะ Google Sheets ให้ส่งออกและกระทบยอดก่อนตัดการเชื่อม
3. สำรองด้วย pg_dump แบบ custom archive รวม schema public และ stock_private (ถ้ามี) พร้อมข้อมูล functions และ grants
4. เก็บนอก GitHub/เว็บสาธารณะ จำกัดสิทธิ์ และบันทึก checksum กับเวลาสำรอง
5. ทดลองกู้คืนบน staging แยก ตรวจจำนวนสินค้า ประวัติ ยอดต่อสินค้า ต้นทุน และบัญชี
6. เก็บเวอร์ชันเว็บเดิม ตรวจชื่อผู้ใช้ซ้ำโดยไม่แยกตัวพิมพ์ใหญ่เล็ก และตรวจรายการ preorders ที่อาจเพิ่มหลังวันที่สำรวจ
7. เว็บรุ่นนี้ไม่มีโมดูลติดตามพรีออเดอร์ ให้ปิดหรือกระทบยอดรายการดังกล่าวก่อน cutover

## ทดสอบ staging
- ใช้สำเนาฐานข้อมูลที่กู้คืนและตั้งค่า src/config.js ของสำเนาทดสอบให้ชี้ staging
- ติดตั้ง migration ใน supabase/migrations/ ภายใน transaction เดียว และหยุดทันทีเมื่อเกิดข้อผิดพลาด
- ใช้บัญชี admin เดิม ไม่มีการสร้างรหัสผ่านเริ่มต้นใหม่
- ทดสอบ staff, รูปเอกสาร, เครื่องสแกนจริง, CSV, สองเครื่องพร้อมกัน, เน็ตหลุด, ส่งซ้ำ และยกเลิกคิว
- ตรวจ RLS/grants และ Supabase Security Advisors; exposed schemas ต้องไม่รวม stock_private
- ตรวจประวัติและยอดเทียบก่อนย้าย

## สลับระบบจริง
- สำรองใหม่หลังหยุดเขียน และยืนยันผลทดสอบที่ commit ที่จะปล่อย
- ติดตั้ง migration ภายใน transaction เดียวก่อนเปิดเว็บใหม่; API เก่าจะถูกปิด
- เผยแพร่เฉพาะ dist ไม่ใช่ repository ทั้งโฟลเดอร์
- ทุกเครื่องปิดแท็บเดิมแล้วเปิดใหม่ เพื่อเปลี่ยน service worker
- เข้าสู่ระบบด้วย admin เดิม ตรวจยอด ประวัติ และสิทธิ์ Staff
- ทดลองเอกสารที่ระบุชัดว่าใช้ตรวจระบบ จากนั้นย้อนเอกสารโดยเก็บประวัติ
- เปิดทำรายการตามปกติหลังตรวจรับครบ

## การกู้คืน
- migration ล้มเหลว: rollback transaction และคงเว็บเดิมไว้
- ยังไม่มีรายการใหม่หลังสลับ: กู้สำเนาก่อนเปลี่ยนและคืนเว็บเดิมได้
- มีรายการใหม่แล้ว: หยุดเขียนและสำรองสถานะปัจจุบันก่อน ห้ามคืน snapshot เก่าทับทันที
- กระทบยอดเอกสารหลัง cutover ก่อนเลือกระหว่างกู้คืนหรือแก้ไปข้างหน้า
- การคืนฐานข้อมูลเก่าจะนำสิทธิ์เดิมกลับมาด้วย ต้องจำกัดการเข้าถึงจนแก้ไขเสร็จ

## GitHub และงานสำรองต่อเนื่อง
PR นำ live_data_backup.json ออกจากเวอร์ชันใหม่ แต่ไฟล์ยังอยู่ใน Git history และ branch เก่า
การล้าง Git history ต้องประสานผู้ใช้ repository แยกต่างหาก ไม่รวมในการปล่อยครั้งนี้
กำหนดผู้รับผิดชอบ รอบสำรองและระยะเก็บตามปริมาณงานจริง แล้วทดสอบกู้คืนเป็นระยะ
